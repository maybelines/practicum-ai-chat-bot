# Задание 1. Исследование моделей и инфраструктуры

## 1. Для чего компании нужен бот

У QuantumForge много документации: около 18 000 Markdown-файлов, 3 000 страниц Confluence и 250 PDF. Каждый месяц появляется ещё примерно 400 страниц. Документы лежат в разных местах, часть информации дублируется и устаревает. Из-за этого новые инженеры тратят на поиск до четырёх часов в неделю.

Заказчиком такого бота, скорее всего, будет технический директор. Ботом будут пользоваться разработчики, поддержка, менеджеры и новые сотрудники. Им нужны разные ответы: кому-то — описание API, кому-то — инструкция по решению ошибки или порядок получения доступа.

Бот должен находить информацию в документах, давать понятный ответ и ссылку на источник. Если ответа нет, он должен сообщать об этом. Повторяющиеся вопросы без ответа можно собирать в список и передавать тем, кто отвечает за документацию.

Для компании важна конфиденциальность: в базе могут быть клиентские спецификации и описания промышленных систем. Поэтому я выбрал размещение моделей на серверах компании. Это могут быть и серверы в её AWS-инфраструктуре. Главное, чтобы тексты не отправлялись внешним сервисам генерации ответов. Для облачных вариантов сначала нужно определить, какие документы разрешено передавать провайдеру.

Права доступа к документам должны сохраняться и при работе с ботом. Например, сотрудник не должен получать сведения из закрытого проекта через ответ модели.

Сравнение основано на документации. На материалах QuantumForge модели пока не тестировались, поэтому точное качество и время ответа нужно будет проверить при запуске бота.

## 3. Сравнение эмбеддингов

Эмбеддинги нужны, чтобы представить текст в виде вектора и находить похожие по смыслу фрагменты. Для локального варианта я выбрал `intfloat/multilingual-e5-base`, которую можно запустить через библиотеку Sentence-Transformers.

| Критерий | Локальная multilingual-e5-base | OpenAI text-embedding-3-small | OpenAI text-embedding-3-large |
| --- | --- | --- | --- |
| Качество поиска | Поддерживает несколько языков, но требует разбиения длинных документов на короткие фрагменты | Недорогой вариант для поиска по смыслу | Более мощный вариант для многоязычного поиска. Насколько он лучше small на документах компании, покажет тест |
| Скорость создания индекса | На CPU обработка большого объёма займёт больше времени; GPU позволяет её ускорить | Можно отправлять тексты пакетами. Скорость зависит от сети и лимитов API | Те же ограничения API; сами векторы крупнее, поэтому их передача и хранение требуют больше ресурсов |
| Размер вектора | 768 чисел | 1 536 чисел по умолчанию | 3 072 числа по умолчанию |
| Стоимость | Оплачиваются вычисления и обслуживание сервера | 0,02 $ за 1 млн токенов | 0,13 $ за 1 млн токенов |
| Передача данных | Тексты обрабатываются на сервере компании | Каждый индексируемый фрагмент отправляется в OpenAI | Каждый индексируемый фрагмент отправляется в OpenAI |

Характеристики приведены в [описании E5](https://huggingface.co/intfloat/multilingual-e5-base), [руководстве OpenAI Embeddings](https://developers.openai.com/api/docs/guides/embeddings) и карточках моделей [small](https://developers.openai.com/api/docs/models/text-embedding-3-small) и [large](https://developers.openai.com/api/docs/models/text-embedding-3-large).

Для оценки объёма приму в среднем четыре фрагмента на Markdown-файл, шесть на страницу Confluence и сорок на PDF:

`18 000 × 4 + 3 000 × 6 + 250 × 40 = 100 000 фрагментов`.

При среднем размере 400 токенов получится около 40 млн токенов. Первичное создание эмбеддингов обойдётся примерно в 0,80 $ для small и 5,20 $ для large. Это только плата за API, без подготовки текстов и хранения индекса. Количество фрагментов и токенов здесь приблизительное.

Скорость нужно измерить на выбранном сервере. Например, при 10 фрагментах в секунду обработка 100 000 фрагментов займёт около 2 часов 47 минут, а при 100 — около 17 минут. Для API с фактической скоростью 200 000 токенов в минуту тот же объём займёт примерно 3 часа 20 минут. Это примеры расчёта, а не результаты тестов. Извлечение текста из PDF и запись индекса займут дополнительное время.

Я выбираю E5-base, чтобы не отправлять документы наружу. Экономия на токенах здесь не главный аргумент: облачные эмбеддинги стоят недорого.

У E5 есть ограничение в 512 токенов на вход. Поэтому планирую разбивать документы примерно по 400 токенов с небольшим перекрытием. Заголовок и служебные префиксы тоже должны помещаться в этот лимит. Для вопросов нужен префикс `query: `, для документов — `passage: `. При смене модели эмбеддингов индекс придётся построить заново.

## 4. ChromaDB и FAISS

FAISS — библиотека поиска по векторам. Она не хранит всю информацию о документах так, как это делает база данных. ChromaDB умеет хранить векторы, тексты и дополнительные поля, например источник или дату обновления.

| Критерий | FAISS | ChromaDB |
| --- | --- | --- |
| Скорость поиска | Есть точный поиск Flat и приблизительные алгоритмы. У Flat время поиска растёт с размером индекса | На одном сервере использует HNSW: приблизительный поиск, где можно менять баланс между скоростью и полнотой результатов |
| Скорость индексации | Для Flat достаточно добавить готовые векторы, обучение индекса не нужно | Нужно построить HNSW и сохранить тексты с дополнительными полями |
| Внедрение | Легко подключить к Python-приложению. Хранение документов и их связей с векторами нужно организовать отдельно | Есть готовые операции добавления, поиска и обновления записей |
| Поддержка | Нужно следить за соответствием документов и индекса, делать резервные копии | Нужно обслуживать хранилище и делать резервные копии; меньше собственного кода для обновления записей |
| Удобство | Подходит для простого приложения с небольшим индексом | Удобнее, когда часто меняются документы и нужны фильтры по их полям |
| Стоимость владения | Бесплатная библиотека, но нужны RAM, диск и время на разработку хранения метаданных | Бесплатная открытая версия; нужны ресурсы сервера и обслуживание. Готовые функции могут сэкономить время разработки |

Для сравнения использована документация [FAISS об индексах](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes), [Chroma об архитектуре](https://docs.trychroma.com/reference/architecture/overview), [настройках HNSW](https://docs.trychroma.com/docs/collections/configure) и [обновлении записей](https://docs.trychroma.com/docs/collections/update-data).

Нельзя заранее сказать, что одна библиотека всегда быстрее другой. Проверять их нужно на одинаковых векторах и оборудовании. При сравнении с HNSW важно учитывать не только время поиска, но и пропущенные подходящие результаты.

Для бота я выбираю **FAISS с точным индексом `IndexFlatIP`**. Если нормализовать векторы, такой индекс можно использовать для поиска по косинусному сходству. Для ожидаемых 100 000 фрагментов разумно сначала проверить этот простой вариант.

Тексты, ссылки, версии и права доступа буду хранить отдельно, для первой версии — в SQLite. Поиск должен учитывать разрешённые пользователю документы. При обновлении нужно сохранять индекс и связанные с ним данные вместе, чтобы бот не ссылался на удалённые или старые фрагменты.

FAISS будет работать внутри контейнера бота, а индекс — сохраняться в постоянном Docker-томе. Отдельный сервер для самой библиотеки не нужен. Если документов и сложных фильтров станет заметно больше, стоит вернуться к ChromaDB: у неё удобнее работа с метаданными.

## 5. Конфигурация сервера

Для начала оценю размер векторов E5. Каждая из 768 компонент в формате float32 занимает четыре байта:

`100 000 × 768 × 4 = 307 200 000 байт`, то есть примерно 293 МиБ.

Сам индекс небольшой, но память нужна ещё для приложения, текстов, модели эмбеддингов и обработки файлов. Поэтому выбирать сервер только по этим 293 МиБ нельзя.

Для первого запуска в компании предлагаю два сервера:

| Сервер | CPU | RAM | GPU | Диск |
| --- | --- | --- | --- | --- |
| Бот, эмбеддинги и FAISS | 8 vCPU | 32 ГиБ | Не нужна | 200 ГиБ SSD |
| Локальная языковая модель | 16 vCPU | 64 ГиБ | NVIDIA L4, 24 ГБ видеопамяти | 100 ГиБ SSD |

Так модель можно обновлять отдельно от приложения. Для учебного стенда всё можно запустить на одном сервере с 16 vCPU, 64 ГиБ RAM, GPU на 24 ГБ и SSD на 300 ГиБ.

В AWS примером сервера для модели служит `g6.4xlarge`: у него 16 vCPU, 64 ГиБ RAM и одна L4. Наличие этого типа сервера нужно проверить в выбранном регионе. [Характеристики AWS G6](https://aws.amazon.com/ec2/instance-types/g6/)

Видеопамять на 24 ГБ рассчитана на Qwen3-14B с 4-битным квантованием. Веса в таком формате теоретически занимают около 7,4 ГБ, но при запуске потребуются ещё память для промежуточных данных и кеша. Начать стоит с контекста до 8 000 токенов и одного-двух одновременных ответов, затем проверить нагрузку. Без квантования, в BF16, только веса займут около 29,6 ГБ и на эту видеокарту не поместятся.

Для вариантов с облачной моделью достаточно первого сервера без GPU. Для начала можно использовать Docker Compose, а позже перенести приложение в существующий EKS. Также нужны резервные копии: два предложенных сервера выполняют разные задачи и не заменяют друг друга при сбое.

## 6. Варианты решения и пример затрат

Я рассмотрел четыре варианта:

| Вариант | Состав | Плюсы | Минусы |
| --- | --- | --- | --- |
| A. Облачный | GPT-6 Luna + OpenAI small + FAISS | Проще запустить, не нужен GPU | Все индексируемые тексты уходят провайдеру |
| B. С YandexGPT | YandexGPT Pro 5.1 + локальная E5 + ChromaDB | Не нужен GPU для генерации, удобно обновлять документы | Найденные фрагменты уходят провайдеру; выбранный тариф выше, чем у Luna |
| C. Локальный | Qwen3-14B + E5 + FAISS | Можно работать с закрытой документацией, нет зависимости от API моделей | Нужны GPU и обслуживание моделей; метаданные хранятся отдельно |
| D. Смешанный | Luna для разрешённых запросов, Qwen для закрытых + E5 + ChromaDB | Можно использовать обе модели в зависимости от данных | Сложнее настроить и проверить; собственный GPU всё равно нужен |

Чтобы сравнить расходы, приму 20 000 вопросов в месяц. На каждый вопрос заложу 4 000 входных токенов вместе с найденными фрагментами и 500 токенов ответа. За месяц это 80 млн входных и 10 млн выходных токенов.

Для Luna с европейской обработкой получится:

`80 × 0,11 + 10 × 0,55 = 14,30 $ в месяц`.

Для YandexGPT Pro 5.1:

`(80 + 10) × 6,557376 ≈ 590,16 $ в месяц`.

Расчёт сделан без скидок за кеш, дополнительных инструментов и режима расширенного рассуждения. Для варианта D приму, что 80% запросов можно отправлять в облако. Тогда на Luna уйдёт около 11,44 $ в месяц, а остальные запросы обработает локальная модель.

Стоимость серверов и обслуживания для примера задам отдельно:

- сервер бота — 0,30 $ в час;
- полный сервер с GPU — 1,50 $ в час;
- диски и резервные копии — 50 $ в месяц;
- обслуживание — 50 $ за час работы инженера;
- серверы работают весь месяц, то есть примерно 730 часов.

Это условные ставки для расчёта, не тарифы AWS. Реальная стоимость зависит от региона, оборудования и договора. Для A и B нужен сервер бота, для C и D — оба сервера из предыдущего раздела.

| Вариант | Серверы и хранение, $/мес | API, $/мес | Обслуживание, $/мес | Всего, примерно $/мес |
| --- | ---: | ---: | ---: | ---: |
| A | 269 | 14,36 | 200 — 4 часа | 483 |
| B | 269 | 590,16 | 300 — 6 часов | 1 159 |
| C | 1 364 | 0 | 500 — 10 часов | 1 864 |
| D | 1 364 | 11,44 | 600 — 12 часов | 1 975 |

В A включены эмбеддинги новых документов и вопросов: примерно 0,056 $ в месяц. Для этого я заложил 0,8 млн токенов новых фрагментов и 2 млн токенов вопросов. Обработку изменённых старых документов нужно прибавить отдельно. В остальных вариантах локальные эмбеддинги вычисляются на уже учтённом сервере.

Часы обслуживания тоже оценочные. В расходы не включены разработка бота, подготовка документов, налоги и резервные серверы. Если оборудование покупается, вместо аренды нужно учитывать его стоимость, срок службы, электричество и обслуживание.

По этому расчёту облачный вариант самый дешёвый. Локальный я выбираю из-за конфиденциальности. Если компания разрешит отправлять весь нужный набор документов внешнему провайдеру, вариант A будет выгоднее. Смешанный вариант имеет смысл, если локальной модели окажется недостаточно для части вопросов. YandexGPT стоит выбрать, если он покажет лучшие результаты на запросах сотрудников или у компании уже будут подходящие условия работы с провайдером.

## 7. Мой выбор

Для проекта я буду использовать **Qwen3-14B с 4-битным квантованием, multilingual-e5-base и FAISS**. Для кода — Python 3.11 и LangChain, для запуска — Docker Compose.

Так документы останутся в инфраструктуре компании, а для поиска не понадобится отдельный сервис базы данных. Основной недостаток — стоимость видеокарты и необходимость обслуживать модель. У FAISS также придётся отдельно организовать хранение текстов, версий и прав доступа.

Перед запуском нужно проверить бота на вопросах разработчиков, поддержки и новых сотрудников: находит ли он нужный документ, правильно ли отвечает, показывает ли источник и честно ли сообщает «Я не знаю». Отдельно нужно проверить закрытые документы и устаревшие версии. Если эти проверки покажут проблемы, можно пересмотреть модель или способ поиска.

# Задание 2. Подготовка базы знаний

## Что взял за основу

Я выбрал [Narutopedia](https://naruto.fandom.com/) и взял 32 статьи: 16 персонажей, 6 деревень, 6 техник и понятий, 2 организации и 2 вида оружия. Из них получился вымышленный мир Эльвар. Тексты оставил на английском, как в источнике.

В `knowledge_base/` лежат только готовые карточки: один файл на одну сущность. Список исходных страниц и новые названия приведены ниже.

## Как подготовил тексты

Вся обработка находится в `scripts/prepare_knowledge_base.py`. Скрипт получает вступления статей через открытый API Fandom, удаляет таблицы, картинки, подписи, сноски и японские написания в скобках. У самых коротких статей он дополнительно берёт первые четыре предложения следующего раздела.

Затем скрипт заменяет имена и термины по `terms_map.json`. В словарь включены полные и короткие имена, фамилии, кланы, деревни, титулы, техники, оружие и названия событий. Например, Naruto Uzumaki стал Taren Elvor, Konohagakure — Nelvar, а Rasengan — Orveth Sphere.

Сначала проверяются длинные названия, чтобы короткое имя не разбило полное. Регистр букв не влияет на поиск. Замена выполняется за один проход и не затрагивает части других слов.

Каждой карточке я добавил свой код архива, которого нет в исходной статье. Само переименование не гарантирует, что модель не узнает сюжет, поэтому для проверки поиска можно задавать вопросы и об этих кодах. Например: «Какой код архива у Taren Elvor?» — ответ `10144833C706`.

В индекс нужно загружать только файлы из `knowledge_base/`. Словарь замен, исходные тексты и этот отчёт в него не входят.

## Как запустить

Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-data.txt
python scripts/prepare_knowledge_base.py
```

Первый запуск скачивает статьи, следующие используют кеш в `.cache/naruto/`. Кеш не попадает в Git. Для повторного скачивания достаточно удалить его перед запуском скрипта.
